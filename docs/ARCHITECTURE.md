# GraphKnows Architecture

## Vision

GraphKnows is a **multi-country political intelligence platform** that transforms
unstructured parliamentary debates, legislation, and policy documents into a
queryable knowledge graph. The system supports:

- Ontology-guided named entity extraction across legal and political domains
- Knowledge graph construction with community detection (Leiden algorithm)
- Hybrid GraphRAG: semantic vector search + graph traversal + LLM reasoning
- Incremental corpus ingestion from public APIs (EP Open Data, legislation.gov.uk)

## Key Design Decisions

### One embedding model, one vector space
All embeddings (chunk text + entity names) use `BAAI/bge-small-en-v1.5` (384-dim).
The model name is a single constant `EMBED_MODEL` in `services/graphrag/graph_store.py`.
Ingest and query paths import from this constant — no drift possible.

### Fine-grained ontology labels preserved end-to-end
- `ontology_label`: raw label from GLiNER2/LLM — never overwritten after extraction
- `coarse_bucket`: analytics grouping only — not stored as a graph property
- Fallback when no label available: `"UNKNOWN"` (not `"Concept"`)

### Entity resolution via Node2Vec
Entities sharing similar co-occurrence contexts are merged using Node2Vec embeddings.
This produces canonical hub entities rather than maximising raw relation count.
Modularity target: > 0.75 (validated with Leiden on full corpus).

### Community detection: Leiden (not Louvain)
Leiden guarantees well-connected communities (no disconnected components within clusters).
Implemented via `leidenalg` + `igraph`. Community summaries generated by LLM (Groq).

### 7-stage pipeline (IterativeOrchestrator)
Each stage has a single responsibility and CC <= 10:
1. `_stage_load_batch` — load document segments
2. `_stage_build_graph` — add to lexical graph
3. `_stage_extract` — NER + relation extraction
4. `_stage_resolve_entities` — Node2Vec + entity merging
5. `_stage_detect_communities` — Leiden community detection
6. `_stage_summarize` — LLM community summaries
7. `_stage_export` — analytics, checkpoints, provenance

### RRF fusion (k=60)
All retrieval tools accumulate candidate chunk IDs. `fuse_and_rank` applies
Reciprocal Rank Fusion across all channels to produce a single ranked result set.
This prevents any single retrieval path from dominating.

## Configuration

All config via environment variables (no hardcoded credentials):

```bash
# Required
NEO4J_PASSWORD=...
PGVECTOR_PASSWORD=...  # not empty, not 'changeme'
GROQ_API_KEY=...

# Optional (have sane defaults)
NEO4J_HOST=172.18.0.1   # Docker bridge IP
NEO4J_PORT=7687
NEO4J_USER=neo4j
PGVECTOR_HOST=172.18.0.1
PGVECTOR_PORT=5432
PGVECTOR_DB=vectordb
EMBED_MODEL=BAAI/bge-small-en-v1.5
```

Copy `.env.example` to `.env` and fill in credentials before running.

## Roadmap

### Near-term (current focus)
- Fix pgvector retrieval: verify chunk embeddings exist post-ingest
- Grow corpus: ingest 110 EP debates + 40 UK SIs for non-trivial graph topology
- Enable multi-label Neo4j nodes (requires APOC or upgrade) for native `MATCH (e:PERSON)`
- Persist `community_id` integer on Topic nodes

### Medium-term
- Multi-country ingestion: EUR-Lex (SPARQL), Bundestag Open Data, Oireachtas API
- Per-country ontology profiles (LKIF base + jurisdiction-specific extension)
- GraphRAG planner + specialists (KAG-Solver architecture, ref. 2501.13958)
- Evaluation harness: RAGAS automated scoring on fixed query set

### Long-term
- Cross-country entity alignment (same person/org appears in multiple parliaments)
- Temporal KG: track how entity relationships change across legislative sessions
- Frontend: live graph visualization of retrieved subgraph per query
- Reasoning transparency: surface ReAct trace in UI for auditability
